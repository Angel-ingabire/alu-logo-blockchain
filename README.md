# ALU Logo Registry DApp

## Project overview

This repository contains a small Ethereum dApp for the African Leadership University (ALU) logo registry and token dashboard. The project combines:

- an ERC-721 registry for storing an ALU logo asset and its SHA-256 digest,
- an ERC-20 token named `ALUT`, and
- a React + Vite frontend that exposes the contracts to a non-technical user through MetaMask and read-only blockchain calls.

The purpose is to allow a user to register a logo file, verify the authenticity of a logo against the on-chain record, and inspect token ownership without requiring direct contract CLI knowledge.

The application addresses a real problem: a logo or file can be copied or modified, and it is difficult to prove which version was officially registered. By storing a file hash on-chain and comparing later submissions to that value, the dApp provides an audit trail and a trusted integrity check.

## Architecture and runtime flow

The application uses a standard browser-wallet stack:

- React frontend (Vite)
- ethers.js v6
- MetaMask or any injected EVM wallet exposing `window.ethereum`
- Ethereum Sepolia test network
- the `ALUAssetRegistry` contract and the `ALULogoToken` contract

High-level flow:

```text
Browser / React UI
  ├─ Web Crypto API (SHA-256 browser hashing)
  ├─ ethers.BrowserProvider(window.ethereum) for MetaMask account + signer access
  ├─ ethers.JsonRpcProvider for read-only contract checks
  └─ Contract calls to Sepolia
          ├─ ALUAssetRegistry (ERC-721)
          └─ ALULogoToken (ERC-20)
```

The frontend uses `BrowserProvider` when it needs a signer or wallet account. A read-only call is made through a provider without prompting for a transaction signature. The app distinguishes between:

- read-only operations: `name()`, `symbol()`, `balanceOf()`, `owner()`, `ownershipPercentage()`, `verifyLogoIntegrity()`, event queries
- wallet-signed transactions: asset registration, or any contract write call that requires MetaMask approval

## Smart contracts

### ALUAssetRegistry

File: `contracts/ALUAssetRegistry.sol`

This contract is an ERC-721 NFT-based registry for ALU branding assets.

It implements:

- `registerAsset(string assetName, string fileType, bytes32 contentHash)`
- `verifyLogoIntegrity(uint256 tokenId, bytes32 suppliedHash)`
- `getAsset(uint256 tokenId)`

The registry:

- mints a sequential token ID for the caller,
- stores the asset name, MIME/file type, hash, registrant, and timestamp,
- prevents duplicate hashes, and
- emits `AssetRegistered` to allow clients to discover a registered asset by event history.

The known canonical ALU logo hash in the project is:

```text
0x407BE7B9AC994BCCA2AB5E0C901B6471A149AA08FC9201F7BF546E6852FB9DDE
```

This is also the expected hash used in the deployment script and Solidity tests.

### ALULogoToken

File: `contracts/ALULogoToken.sol`

This contract is an ERC-20 token with `Ownable` and a fixed total supply.

Important properties:

- Name: `ALU Logo Token`
- Symbol: `ALUT`
- Total supply: `1_000_000 * 10^18` base units = `1,000,000 ALUT`
- Ownership: the deployer/initial owner is the sole initial token owner

Functions implemented:

- `distributeShares(address recipient, uint256 amount)`
- `ownershipPercentage(address account)`

`distributionShares` is restricted to the contract owner and checks for a valid recipient and positive amount before transferring tokens.

## Actual frontend functionality

The frontend is implemented under `frontend/src/App.jsx` and uses `ethers.js` together with the JSON ABIs generated by Hardhat.

### 1. Wallet connection

The app checks for `window.ethereum` and uses `BrowserProvider` to request account access through MetaMask. The connection flow is:

- check wallet availability,
- call `provider.send("eth_requestAccounts", [])`,
- read the connected account,
- read the network,
- refresh wallet and contract data.

This is a browser-side wallet interaction and requires a user to approve the wallet request.

### 2. Displaying wallet address and ALUT balance

Once connected, the app reads:

- `balanceOf(address)` for the current wallet,
- `totalSupply()` for the token,
- `owner()` for the token owner,
- `ownershipPercentage(address)` for the connected account.

This is performed with direct wallet-connected contract reads and does not require a transaction.

### 3. Contract information reads

The app reads basic contract metadata such as token name, symbol, total supply, and owner. Read-only calls are used for public data and do not require a user-signed transaction.

### 4. Uploading an image and hashing it in-browser

The frontend includes a file upload flow that accepts an image file, shows a preview, and computes a SHA-256 digest in the browser using the Web Crypto API. The digest is converted to a 32-byte `bytes32`-style hex value.

### 5. Registering an asset

The asset registration flow:

- accepts a name and file type,
- verifies the file is not empty,
- computes a file hash,
- invokes the registry contract method `registerAsset(...)`,
- waits for the transaction to confirm,
- shows the resulting token ID and metadata.

This requires a MetaMask transaction approval and a wallet signer.

### 6. Verifying an asset by uploaded file or pasted hash

The app includes a public verification screen that can:

- upload a file and compute a hash locally, or
- accept a pasted `0x` hash,
- read the registry and compare the supplied hash to the registered content hash,
- display whether the file matches the canonical registered logo.

This verification path is read-only and does not require a wallet to sign.

### 7. Token ownership dashboard

The token dashboard shows:

- the connected wallet balance,
- token supply,
- current ownership percentage,
- owner address,
- current holder list when available.

### 8. Owner-only token distribution

The owner-only distribution form is available only when the connected wallet is the contract owner. It:

- validates the recipient address,
- validates a positive amount,
- ensures the owner has sufficient balance,
- submits `distributeShares(recipient, amount)` via the signer,
- refreshes the connected wallet balance and recipient balance after confirmation.

### Features that do not require a wallet

These are read-only and do not require a wallet connection:

- logo verification by uploaded file,
- hash verification,
- contract metadata reads,
- public registry lookup checks,
- contract reading such as `name()`, `symbol()`, `owner()`, `totalSupply()`, and `ownershipPercentage()` when called on a provider.

### Features that require wallet connection and transaction approval

These require a connected signer and MetaMask approval:

- asset registration,
- token distribution,
- any write function call that changes blockchain state.

## Installation and execution

### Install dependencies

```bash
git clone https://github.com/Angel-ingabire/alu-logo-blockchain.git
cd alu-logo-blockchain
npm ci
npm --prefix frontend ci
```

### Configuration

The Hardhat deployment scripts rely on root environment variables in `.env` and read them using `dotenv/config`.

The script `scripts/deploy.js` expects these values:

```dotenv
SEPOLIA_RPC_URL=https://...
SEPOLIA_PRIVATE_KEY=0x...
EXPECTED_OWNER_ADDRESS=0x55D23cA45Eace7E4497C780f89eac62f61421B3E
```

The frontend uses public Vite variables in `frontend/.env.local`. Start from the committed `frontend/.env.example` template:

```bash
Copy-Item frontend/.env.example frontend/.env.local
```

The template selects Sepolia and contains the existing deployment addresses and a public RPC endpoint. The app also safely falls back to those recorded Sepolia defaults when a setting is absent, blank, or a placeholder. A custom RPC endpoint or contract address can be supplied through the same variables.

Example public frontend settings:

```dotenv
VITE_NETWORK=sepolia
VITE_SEPOLIA_RPC_URL=https://...
VITE_SEPOLIA_ALU_ASSET_REGISTRY=0x93B4124B9673f520457577819B525E40abEc8F57
VITE_SEPOLIA_ALU_LOGO_TOKEN=0xc83E78175eD2c5f07Dcc8143D153cbB181d57730
VITE_SEPOLIA_TOKEN_HOLDER_ADDRESSES=
```

The token dashboard can show example holder rows when `VITE_SEPOLIA_TOKEN_HOLDER_ADDRESSES` contains at least three comma-separated, verified Sepolia addresses. It reads each configured address's current balance from the token contract; it does not scan Transfer history or supply default/example addresses. Leave this setting blank until verified holder addresses are available.

Important: Vite variables are exposed to the browser. Do not place private keys, seed phrases, or other secrets in any `VITE_` variable. The root `.env.example` is only for deployment configuration; keep any real deployment credentials in the ignored root `.env` file.

## Known limitations and honest status

The project is functional for local mock validation and for read-only contract interaction when the correct Sepolia configuration is supplied. However, there are some genuine limitations:

- The dashboard intentionally does not scan historical `Transfer` events and does not claim to show a complete holder list.
- No verified example holder addresses are currently configured. The dashboard will show example rows only after at least three addresses are configured in `VITE_SEPOLIA_TOKEN_HOLDER_ADDRESSES`; it reads their live balances and calculates ownership from those balances and `totalSupply()`.
- The frontend tests are mock-based and do not assert real-chain wallet behavior.
- The project does not include a live browser screenshot or demo video in the repository.
- The deployment metadata is ignored by Git, so public deployment URLs and addresses must be recorded in the README or submission materials.

## Token dashboard example holders

The dashboard uses only manually configured, verified Sepolia addresses for its example rows. It reads each current balance with `balanceOf()` and derives the percentage from that balance and `totalSupply()`. It does not retrieve historical `Transfer` logs, infer a deployment block, or present the examples as a complete holder list. The environment variable is intentionally blank in the committed template until verified addresses are available.
