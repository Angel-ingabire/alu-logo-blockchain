## Problem and solution

An official logo can be copied or modified without an obvious visual difference. The registry stores a SHA-256 digest and metadata on Ethereum so a visitor can compare an exact file's digest with a registered value. The token contract represents a fixed ALUT supply and restricts distribution to its owner. The browser dApp provides wallet-based registration and token distribution, with public read-only verification.

## Features

- MetaMask-compatible injected wallet connection, account and chain-change listeners, local app disconnect, and a `wallet_switchEthereumChain` action for the selected network.
- Ethers.js v6 contract instances using ABI JSON generated by Hardhat.
- Browser-side SHA-256 with Web Crypto, image preview, and `bytes32`-formatted hash.
- Wallet-signed asset registration and receipt/event parsing for the new token ID.
- Public file/hash verification using a read-only JSON-RPC provider and `AssetRegistered` log discovery.
- Token supply, connected wallet balance, integer ownership percentage, event-derived holders, and an owner-gated distribution form.

The Sepolia address values in the checked-in frontend defaults are zero addresses. Configure the frontend's public Vite variables below before expecting the frontend to use the deployed Sepolia contracts.

## Architecture

```text
Browser
  React UI
   |-- Web Crypto API: SHA-256 of selected file
   |-- Ethers.js BrowserProvider --> MetaMask (account, chain, signed writes)
   |-- Ethers.js JsonRpcProvider --> configured public RPC (read-only verification)
                                      |
                                  Ethereum Sepolia
                         +------------+-------------+
                         |                          |
                 ALUAssetRegistry              ALULogoToken
                   ERC-721                       ERC-20
```

The write path obtains a signer from MetaMask and waits for a transaction receipt. Public verification uses a JSON-RPC provider and does not ask a visitor to connect a wallet or sign a transaction. The ABI is the machine-readable contract interface used by Ethers.js to encode calls and decode return values and events.

## Smart contracts

### `ALUAssetRegistry`

`ALUAssetRegistry` inherits OpenZeppelin ERC-721 and has no constructor arguments. `registerAsset(assetName, fileType, contentHash)` is public, mints a sequential NFT to the caller, stores the metadata (including registrant and timestamp), marks the content hash as registered, and emits `AssetRegistered`. It rejects empty names/types, a zero hash, and duplicate hashes. `getAsset(tokenId)` returns stored metadata. `verifyLogoIntegrity(tokenId, suppliedHash)` compares a supplied digest with that token's stored digest.

Registration is intentionally not restricted to an ALU administrator in the contract. A stored registration therefore proves what content was recorded and by whom, not institutional authorization of the registrant. Only the digest and text metadata are stored; the image itself is not.

### `ALULogoToken`

`ALULogoToken` inherits OpenZeppelin ERC-20 and Ownable. Its constructor accepts `initialOwner`, names the token `ALU Logo Token` (`ALUT`), and mints `1,000,000 * 10^18` base units (1,000,000 tokens at 18 decimals) to that owner. The recorded deployment metadata identifies Account 1 as deployer and token owner.

`distributeShares(recipient, amount)` is `onlyOwner`, rejects a zero recipient and zero amount, and transfers tokens from the owner. OpenZeppelin ERC-20 also rejects transfers exceeding the owner's balance. `ownershipPercentage(account)` returns integer percentage points using floor division, so holdings below one percent display as zero; it is not a fractional percentage API. Ownership can be transferred through inherited Ownable functionality.

## User workflows

### Register an asset

Open **Register Asset**, enter the asset name and file type, and select an image. The browser previews the image and computes SHA-256 over its bytes, formatted as a `0x`-prefixed 32-byte value. Submit **Register Asset** and approve the transaction in MetaMask. The UI waits for confirmation and reads the `AssetRegistered` event to show the NFT token ID. Duplicate hashes are rejected by the contract and mapped to a UI message.

The form checks that the image is non-empty and has an `image/*` MIME type. This is a client-side file-type check, not content sniffing; the file itself is not uploaded or stored on-chain.

### Verify a logo publicly

Open **Verify Logo** without connecting a wallet. A visitor can upload an image or paste a hash. The frontend scans `AssetRegistered` event history to discover a token by digest, then reads the registry and calls `verifyLogoIntegrity()`. A match displays the stored name, file type, registrant, and timestamp. A mismatch displays a warning. A read-only provider call does not require the visitor to sign a transaction or pay gas.

The current UI still displays an optional Token ID input, but the verification handler discovers the ID from events and does not use that input. Event scanning covers registry history and may become slower or unavailable with RPC providers that limit historical logs. The Sepolia address variables must be configured for this screen to query the deployed registry.

### Inspect and distribute ALUT

Connect a wallet to read the connected address's balance, total supply, owner, and integer ownership percentage. The dashboard obtains candidate holders from ERC-20 Transfer events, queries current balances, and labels illustrative examples as illustrative rather than chain data when fewer than three real addresses are discovered. Event-derived addresses may include former holders with zero current balance.

Only the contract owner sees the distribution form, and the contract's `onlyOwner` check is the authoritative access control. The contract rejects zero recipient and zero amount and rejects amounts exceeding the sender balance. The frontend checks that fields are non-empty, but does not prevalidate the recipient address, positive amount, or sufficient balance; invalid values are ultimately rejected by parsing or the contract. After confirmation, the app requests updated balance, percentage, and holder entries.

## Security and known limitations

- Wallet-signed calls keep transaction approval with the user; public verification uses a read-only provider.
- Contract-level owner authorization, duplicate hash protection, and basic argument checks are implemented.
- Private keys belong only in the ignored root `.env` for Hardhat scripts. Vite `VITE_` variables are public and bundled into browser assets.
- The registry does not restrict who may register an asset or validate that the registrant represents ALU.
- Logo bytes are not stored; integrity is based on the submitted digest and metadata.
- Frontend Sepolia address defaults are zero and must be configured in `frontend/.env.local`; the frontend does not consume deployment JSON automatically.
- Full-history event discovery has no pagination or indexed digest filtering.
- The public verification file handler lacks an explicit user-facing catch for hash-generation failures; MIME type is not proof of actual file format.
- Distribution form validation is incomplete on the client; the contract remains authoritative.
- The owner can transfer ownership using inherited Ownable functionality, so the initial account is not permanently exclusive.
- `ownershipPercentage()` uses integer rounding.
- The root `deploy` npm script still selects `localhost`, while `scripts/deploy.js` requires the `sepolia` network. Do not use that script entry without correcting/documenting its target. This README task did not alter deployment code or package scripts.
- The deployment metadata is ignored by Git. Keep public deployment references in the README or include a reviewed public metadata record explicitly in a submission archive; never include `.env`.
- The existing frontend test suite is mocked and does not demonstrate live wallet/network or deployed-contract behavior.

Potential future work includes fuller integration tests against a local node, precise decimal ownership percentages, robust recipient/balance validation, paginated/event-indexed registry discovery, transaction history, IPFS or another content-addressed asset store, WalletConnect, responsive testing, and governance/voting contracts. These are proposals, not implemented features.
